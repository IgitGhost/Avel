# Windows Sandbox test harness

Destructive end-to-end tests (installing and uninstalling real programs, leftover removal,
forced removal, install tracing) run in [Windows Sandbox](https://learn.microsoft.com/windows/security/application-security/application-isolation/windows-sandbox/),
a disposable VM that is wiped when it closes.

## One-time setup

Windows Sandbox needs Windows 10/11 Pro or Enterprise. Enable it from an elevated PowerShell, then reboot:

```powershell
Enable-WindowsOptionalFeature -Online -FeatureName Containers-DisposableClientVM
```

## Usage

The sandbox has neither Qt nor the MSVC runtime, so make the build self-contained first:

```powershell
cmake --build --preset release --target deploy
.\tests\sandbox\Start-AvelSandbox.ps1                  # maps build\release\bin
.\tests\sandbox\Start-AvelSandbox.ps1 -WaitForReport   # also waits for and prints the smoke-test report
.\tests\sandbox\Start-AvelSandbox.ps1 -Preset debug
```

Inside the sandbox:

| Path | Contents | Access |
|---|---|---|
| `C:\Avel\bin` | The build output, on `PATH` | Read-only |
| `C:\Avel\sandbox` | This folder | Read-only |
| `C:\Avel\results` | Reports from the scenarios; shows up on the host as `build\sandbox\results` | Writable |

Only one sandbox can run at a time; `-ReplaceRunning` stops a running one first, and
`-CloseWhenDone` (with `-WaitForReport`) closes it after the report arrives.

## Scenarios

`-Scenario <name>` runs `scenarios/<name>.ps1` at logon. Each writes `results\<name>.txt` last.

| Scenario | What it checks |
|---|---|
| `logon` (default) | `avel-cli version` runs and the GUI starts |
| `uninstall` | Phase 2 acceptance: installs one sample per installer technology and removes each interactively. `scenarios/clicker.ps1`, a separate PowerShell process, clicks through the uninstallers' dialogs in English or Russian. Then it reinstalls them, removes all five in one quiet batch with a System Restore point, and removes two through the GUI. Also writes `uninstall.json` (avel-cli's output), `uninstall.log` (progress while it runs) and `clicks.log` (every window the clicker saw, with its buttons and clicks) |
| `leftovers` | Phase 3a acceptance (the leftover scan only reads): installs the five samples and previews their leftovers with `avel-cli scan`, then removes them in one quiet batch and checks the scan that follows. Notepad++'s context-menu sparse package must be reported as a package leftover, and no reported item may be, or contain, a special folder, a profile or a drive root, lie in the Windows folder or be a SYSTEM key (an oracle built from .NET's special folders, independent of Avel's protection rules). Also writes `leftovers.json` and `leftovers.log` |
| `removal` | Phase 3b acceptance: installs three samples and `Contoso Fixture` (`scenarios/fixture.ps1`). The fixture's uninstaller leaves one leftover of every kind: folders, a shortcut, keys, a Run value, a service, a task, a COM class with its shell extension, and a firewall rule. The scenario also installs canaries named after it in `C:\Windows`, `ProgramData\Microsoft`, `AppData\Roaming\Microsoft` and `HKLM\SOFTWARE\Microsoft`, and a program of the same publisher that stays installed. It runs `uninstall --remove-leftovers --allow-irreversible`, then compares `avel_state_dump` dumps: every fixture leftover and Notepad++'s sparse package must be gone, and the rest unchanged. Then `undo --item` and `undo` must give back identical dumps. Then it reinstalls the fixture and kills the removal after 7 journal records (`AVEL_TEST_FAULT_AFTER`); the next run must settle the set, and undo must restore it exactly. Last, the GUI round (Phase 3c) reinstalls the fixture and uninstalls it through `avel.exe` with UI Automation: the leftover dialog must open by itself, Remove must take every fixture leftover away, and the Undo Center's Restore all must give back identical dumps. Also writes `removal.json` and `removal.log` |
| `force` | Phase 4 acceptance (Avel Force, which never runs the program's uninstaller). Round 1 installs `Contoso Fixture` and the canaries, deletes the fixture's uninstall script and starts its app. `uninstall` must refuse with `uninstaller-missing`, `force --exe` must find the program from its file, and `force --yes` without `--end-processes` must end and remove nothing. `force --yes --end-processes` must end the app and remove the program's folder, its Uninstall key and every leftover, leaving the canaries, the other program and the firewall rule alone; undo must give back identical dumps. Round 2 installs 7-Zip's MSI from a copy, then deletes the copy and Windows Installer's cached package. `uninstall` must refuse with `msi-package-missing`, `force` must remove the program with Windows Installer's registration (product keys, install properties, upgrade code, components) until Windows Installer no longer knows the product, and undo must give the registration back exactly. Round 3 forces a folder no Uninstall entry describes, which must go alone, and `force --folder` must refuse Program Files, `System32` and `C:\Users`. Round 4 adds a dead entry (an Uninstall key whose uninstaller and folder are gone): `list --broken` must show it with its reasons, and `force` must remove the key alone, which undo gives back. Round 5 runs the volume reading unit tests elevated, then `C:\Tools\Contoso Fixture` must be found by `scan --deep` only, at questionable. Round 6: `orphans` must list a folder nobody owns, and none of the installed programs' folders, a folder named after an installed program's publisher, or Windows' folders. Round 7 (Phase 4c) starts the fixture's app again and drives `avel.exe` with UI Automation. The uninstall dialog must offer "Force uninstall…". After "Search the whole disk", the forced-removal review must list `C:\Tools\Contoso Fixture`. Remove must ask to end the app and end it, and the program and its leftovers must go while the unchecked deep-search folder stays. The Undo Center's Restore all must then give back identical dumps, and Tools > Find orphaned folders must list the folder nobody owns. Also writes `force.json` and `force.log` |
| `trace` | Phase 5a and 5b acceptance (Avel Trace, the install tracker, and removing programs by their traces), checked against an independent oracle: `avel_capture` (`tests/helpers/capture.cpp`) lists every file on C:, the registry roots the tracker watches and the environment keys whose values it saves exactly, with plain Win32 calls, right before and right after each traced installation, and their diff is what really changed. The scenario keeps its coarse exclude list as data and logs, per round, how many lines each pattern took out. In rounds 0, 0b and 1 both captures are taken while the trace is open (a line whose item changed again inside the trace but outside the captures is KNOWN only with evidence: a journal record of its name in its folder, or its key's last write time); around `trace run` (rounds 2-4) a difference is put down to the moments between a capture and the trace (KNOWN) only with evidence that it changed then: its creation or last write time, its key's last write time (for a gone key or value, that of the nearest key above it still there), or a watch of the volume's names that saw it go away or appear then, within the trace's own window (its trace.json). First it runs the tracker's unit tests that need elevation. Round 0 traces an idle minute (a stock app opened and closed): no change may be reported that isn't noise, and the trace must account for every line of the diff; it logs the noise by reason and the registry snapshot and diff times, and what the trace didn't account for is logged as KNOWN in the later rounds. Round 0b deletes one of Windows' sounds and renames another between `trace start` and `trace stop`: in a container (the Sandbox) the trace must report exactly that deletion and rename, never the tombstones the container leaves, as created. A created item the volume's journal has no record of between the captures is logged as KNOWN. Round 1 installs `Contoso Trace Fixture` (`scenarios/trace_fixture.ps1`, a scripted installer that creates one item of every kind and edits the machine and user PATH, a machine variable, both SharedDLLs counts and an unrelated value) between `trace start` and `trace stop`. Every line of the oracle's diff must be accounted for by a reported change of the same kind, noise included (completeness), and every reported change that isn't noise by a line of the diff (precision; services, tasks and firewall rules are checked item by item instead). Each item must be reported as such: the program's folder as one item, the keys, values, folders, service, task, its new task folder and firewall rule, and the known values with their exact before and after. Round 1's 5b part: `trace show --json` must show the trace linked to the fixture by itself (by the Uninstall key it created) and every item the fixture created tied to it; `trace export` must write one `avel-trace` file. The user then adds their own `Path` entries (machine and user, the user's unexpanded), and `force <the fixture>` reverts it by its trace inside a manual "watch" trace, between oracle captures and `avel_state_dump` dumps. **Revert:** every line of the oracle's diff between the capture before the install and the one after the removal is judged by the install's own change (not noise) that accounts for it: it must be gone, or be KNOWN, and the KNOWN set is exactly Theme (changed by the installer, never offered), the firewall rule (never removed), protected creations (in the Windows folder, Package Cache, `HKLM\SYSTEM` or keys Windows relies on, restated in the scenario, each line below them protected too), the user's own `Path` entries, and what isn't the fixture's own and the scan left below the removal threshold (listed with its level and evidence). Theme, the rule and both `Path` values must be among them, and both `Path` values must be exactly the value before the install plus the user's entry; the shared DLL's `SharedDLLs` count must be back at 1, the fixture's own count and `CONTOSO_HOME` gone. A line nothing of the install accounts for is noise or changed after the install (logged), unless what the removal took covers it (it fails). The fixture's items must each be planned, done and tied, its five value edits made, and Theme, the rule and the shared DLL never planned; `leftover_scan.traces[]` must name the trace and the program, with counts that add up to the trace's changes. **Undo** must give back identical state dumps, and the oracle's diff between the capture before the removal and the one after the undo may hold only the watch trace's noise, the Task Scheduler's new id and file for the task it registers again, the Start menu's own state that the install changed too, the shell's record of the fixture's shortcut made once more when the undo gives the shortcut back (a new `UFH\SHC` value with the install's data), the shell's records of the handlers it has seen for file types (empty `REG_NONE` values in `FileExts\<extension>\OpenWithProgids`), and a container's base-layer item the volume's journal has no record of between the captures. Then the trace is deleted, imported again (its origin named, linked to the fixture again) and linked by hand (`manual`, primary); the fixture's own uninstaller removes its folder and key, and `force --trace <the imported trace>` (target `trace:<id>`) reverts the rest, judged the same way, and is undone. Rounds 2-4 trace 7-Zip (MSI), Notepad++ (NSIS) and Inno Setup through `trace run`, which must end by itself (`installer-done`) and be complete; precision exceptions are logged. Their 5b part: the trace's primary link must be the sample's own entry (otherwise nothing is uninstalled); `scan` must preview each with its trace, something of it tied; `uninstall --quiet --remove-leftovers` must name the round's trace in `results[].trace`, report sensible trace counts (something gone after the uninstaller), remove every planned item (Notepad++'s sparse package goes only with `--allow-irreversible`, KNOWN), and leave only what Revert puts down as KNOWN, as above (untied items below the removal threshold listed with their level, and the sparse package's registration while the package stays registered); retention must then start the trace's 30 days (`unresolved_since`). Round 5 runs the fixture through `trace run`, starting its app at the end: done within 45 s, the app listed under `left_running` and still running. Round 6 kills a `trace run` after its snapshot, which `trace stop` must then finish, and replaces the USN journal during a trace, which must end incomplete with C: `replaced` and its registry part still reported. Last comes the GUI round (Phase 5c, below under `trace_gui`). The oracle and its checks are in `scenarios/trace_oracle.ps1`, shared by both scenarios. Takes about 30 minutes (`-TimeoutSeconds 3600`). Also writes `trace.json`, `trace.log` and `trace-oracle-<round>.txt` (each round's oracle diff, every line with what accounted for it; `-revert` and `-undo` ones with what judged each line) |
| `trace_gui` | Phase 5c acceptance: the GUI round of `trace` on its own (`scenarios/trace_gui_round.ps1`), `avel.exe` driven with UI Automation and judged with the same oracle and KNOWN rules. 1: Trace > Install and trace… with 7-Zip's MSI (`/qn`): the progress dialog runs, the trace stops by itself (`installer-done`) and the review opens with `C:\Program Files\7-Zip` among the items tied to 7-Zip; the trace is linked to 7-Zip's entry and complete against captures around it (as rounds 2-4). 2: Trace > Start tracing… around `Contoso Trace Fixture`'s installer: the status bar says "Tracing since …", its Stop tracing finishes the trace and opens the review; the trace is linked to the fixture, complete against captures inside it (as round 1) and reports each of its items. In the review the fixture's task folder `\Contoso Trace` is unchecked (from the keyboard, or with clicks on its check box: Qt offers no UI Automation pattern that checks a row), and `trace show` must mark it, and only it, `excluded`. That item is chosen because only the trace finds it and the fixture's own uninstaller leaves it; an item the leftover scan finds by its name is still listed by the scan, but never checked automatically. 3: the program list's Trace column says "Traced" for both, and Trace > Traces… lists both traces. 4: the user adds their own `Path` entries; the fixture is uninstalled from the program list: the uninstall dialog offers "Use the install trace", checked, the leftover review opens by itself with the trace's items and value edits, and without the excluded task folder (or with it unchecked); Remove. In step 1 the round clicks in `avel.exe` between the first capture and the trace's start, so Explorer's record of Avel's own window (`UserAssist`, user-activity noise) may be created then and modified in the trace: that line alone is KNOWN as reported with the other kind. 6 (optional, `$guiOptionalSteps`): Trace > Traces… > Revert by trace… for the fixture's trace (Avel Force by its id) removes what step 5 restored but the excluded folder, undone with `avel-cli`; and a trace started in the GUI and left open when `avel.exe` is ended is finished from the prompt at its next start. Takes a few minutes (`-TimeoutSeconds 1800`). Also writes `trace_gui.json`, `trace_gui.log` and `trace-oracle-gui-<step>.txt` |

**Don't keep files in `build\sandbox\results` open on the host while a scenario runs.** A host
process that holds one open, such as `tail -f`, makes the sandbox's appends to it fail ("being
used by another process"). The scenarios cope: the report is assembled in memory and written at
the end. The progress logs lose their lines, though.

**The clicker** finds classic buttons (msiexec, NSIS, Inno's `TNewButton`, WiX Burn, message
boxes and task dialogs) as child windows with `EnumChildWindows`, and presses them by posting
`WM_COMMAND` to their parent. Managed UI Automation, which PowerShell offers, reports these
buttons as panes without an Invoke pattern, so it's only the fallback for buttons that have no
window of their own. To try the clicker on a dev machine, pass `-WindowTitle <regex>`: it then
touches only matching windows.

**The GUI rounds** (`removal`, `force`, and `trace`'s, which `trace_gui` runs alone) drive
`avel.exe` in English with the UI Automation helpers in `scenarios/gui.ps1`. Qt's own widgets do
expose their buttons, check boxes, menus and tree rows. The helpers look elements up afresh each
time, because Qt's provider invalidates references when the UI changes. Avel Trace's dialogs name
their widgets (docs/trace.md, "The GUI"); Qt's automation id joins an object's name with those of
its named parents, so the helpers match its end. Qt makes only the cells inside an item view's
viewport its children in UI Automation, so `Tree-Items` sees only the rows in view; `Get-ViewRows`
and `Get-ViewCells` read every row through the view's Grid pattern. Checking a row of an item view
(the trace review) takes real input: a click on the first row, Down, Space, or a click on the row's
check box, in physical pixels. A checkable cell's Toggle pattern tells its check state, but its
Toggle didn't change it.

The `uninstall`, `leftovers`, `removal`, `force`, `trace` and `trace_gui` scenarios need the sample installers
(`scenarios/samples.ps1` lists them). Download them once (and build the test MSIX) with `Get-SampleInstallers.ps1`; they
land in `installers/`, which git ignores:

| Installer technology | Sample |
|---|---|
| MSI | 7-Zip (.msi) |
| NSIS | Notepad++ (latest release) |
| Inno Setup | Inno Setup (latest release) |
| WiX Burn bundle | Visual C++ Redistributable x64 |
| MSIX | Avel Test Package (unsigned, built locally with makeappx) |

```powershell
.\tests\sandbox\Get-SampleInstallers.ps1
.\tests\sandbox\Start-AvelSandbox.ps1 -Scenario uninstall -WaitForReport -TimeoutSeconds 1500 -CloseWhenDone
```
